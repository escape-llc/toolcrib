# Tree-shaking audit — module-scope side effects in vendored source

Toolcrib is never an npm dependency — `toolcrib init` copies `src/theme`,
`src/eventBus`, `src/observer`, `src/components/**` directly into a
consumer's own repo (`AGENTS.md`'s own "What this is" section), and
`src/index.ts` (generated by `scripts/generate-index.js`) is the one barrel
file a consumer imports through (`import { Button } from '#toolcrib'`). A
plain `export * from './some/path'` re-export chain **is** tree-shakeable by
every modern bundler (Vite/Rollup/esbuild, webpack 5) — but only if nothing
it transitively imports does real work at module top level. This skill's
whole job is finding the files that do.

**A "module-scope side effect" means code that runs the instant the module
is imported** — not inside a function, hook, component body, or `useEffect`.
A hook that calls `document.querySelector(...)` when it runs is fine (it only
executes if a component actually calls that hook); a bare `document.title =
'x'` sitting at the top of a file, outside any function, is not — it runs for
every consumer who imports that file transitively, whether or not they ever
use what it exports.

Verify every claim below against current source before reporting — this was
last confirmed by a full read of `src/theme/registerThemeSlices.ts`,
`src/theme/themeContext.tsx`, `src/theme/slice.ts`, `src/eventBus/eventBus.ts`,
`src/observer/observerManager.ts`, and `scripts/generate-index.js` on
2026-09-24, and may have drifted since (a new component's `*Slice.tsx` file,
a new observer, a refactor of the registration mechanism).

## 1. The known, confirmed finding — re-verify it still holds, don't assume it's fixed

**`src/theme/registerThemeSlices.ts` is a real, unconditional top-level
side-effect module.** It has no exports of its own — it exists purely to run,
at module scope, one `globalThemeSliceRegistry.register(XSlice)` call per
component (currently ~50), e.g. `globalThemeSliceRegistry.register(CardThemeSlice)`,
`globalThemeSliceRegistry.register(ButtonThemeSlice)`, and so on for every
component with a registered slice. It's reached via a bare side-effect import
(`import './registerThemeSlices';`) from two places: `src/theme/themeContext.tsx`
(where `ThemeProvider` — essentially mandatory for any real consumer — lives)
and `src/theme/serverThemeCSS.ts`. Since `themeContext.tsx` is barrel-exported
wholesale, **importing `ThemeProvider` alone drags in the registration wiring
(and therefore the bundled code) for all ~50 components' slice files**,
regardless of which components the consumer actually imports or renders —
including whatever those slice files themselves import (e.g. `ButtonSlice.tsx`
pulls in `ThemeEditorFieldRow`).

Re-confirm this is still the shape by reading `registerThemeSlices.ts`'s own
current line count/import list and grepping for `import '\./registerThemeSlices'`
— if a future refactor made registration lazy (e.g. gated on first
`useSliceOverrides` call for that specific slice, or resolved via a dynamic
`import()` per component file), this finding is stale and should be reported
as fixed, not repeated.

## 2. General sweep — is there a second offender?

Grep for real top-level side effects across the four vendored directories
(`src/theme/**`, `src/eventBus/**`, `src/observer/**`, `src/components/**`
only — not `demo/`, `scripts/`, or `src/__tests__/`, none of which ship):

```
grep -rn "aiBus\.on(\|document\.\|window\.\|addEventListener(" src/theme src/eventBus src/observer src/components
```

For every hit, confirm it's inside a function/hook/component body, not at
module scope. Two known, already-assessed exceptions — confirm they're still
inert, don't re-report them as new findings:

- `src/eventBus/eventBus.ts`: `export const aiBus = new AIEventBus();` is a
  module-scope singleton, but its constructor only sets up empty Maps/Sets —
  no DOM/global access, so it isn't itself a bundle-size or side-effect
  concern in isolation (though anything that imports `aiBus` at all obviously
  keeps the whole `AIEventBus` class).
- `src/observer/observerManager.ts`: `export const observerManager = new
  GlobalObserverManager();` is a module-scope singleton whose constructor
  *does* call `window.addEventListener('resize', ...)` and construct real
  `ResizeObserver`/`IntersectionObserver`/`MutationObserver` instances —
  genuinely side-effecting, guarded by a `typeof window === 'undefined'`
  check for SSR safety. This only matters for consumers who import something
  that reaches this module (`useAdaptiveSize`, `useMutationObserver`) — it
  does not get pulled in by unrelated components the way
  `registerThemeSlices.ts` does, so it's a normal, scoped side effect rather
  than a tree-shaking defeat. Re-verify this scoping claim (that nothing
  *unrelated* transitively imports `observerManager.ts`) rather than trusting
  it by citation alone.

Also check the "auto-registration into a shared registry at import time"
*pattern* specifically, not just DOM/global access — a future feature could
introduce a second registry (an icon registry, a validator registry,
anything with a `register()`/`globalXRegistry` shape) with the same eager,
unconditional-at-import-time mistake `registerThemeSlices.ts` already made
once. `src/theme/slice.ts` itself is clean (confirmed: `ThemeSlice` is a
plain interface, `ThemeSliceRegistry` a plain class, and an individual slice
file like `CardSlice.tsx` just exports a plain object with no module-scope
registration call — the side effect is entirely concentrated in
`registerThemeSlices.ts`, not distributed per-slice) — a fix here should keep
that property, not spread the side effect back out across every slice file.

## 3. Barrel and generator sanity check

`scripts/generate-index.js` (`renderIndexTs()`) should still only ever emit
plain `export * from '<path>';` lines grouped under comment headers — no
initialization code, no eager side-effect imports added to the generated
`src/index.ts` itself. If a future change to the generator adds anything
beyond a re-export line, that's a second, independent way to reintroduce this
whole class of bug — flag it even if `registerThemeSlices.ts` itself is
eventually fixed.

## 4. Consumer-facing docs — is the limitation (or the fix) actually documented?

Grep `ai-docs/NEW_APP.md`, `ai-docs/REFACTOR_APP.md`, `ai-docs/CORE.md` for
`sideEffects`, `tree-shak`, `tree shak`, `bundle size` (case-insensitive). As
of this skill's authoring, there are zero matches — the docs shipped to
consumers say nothing about the barrel's tree-shaking properties, in either
direction. If `registerThemeSlices.ts`'s eager registration is ever fixed,
confirm whether it's worth a line in `CORE.md`'s own prose section (regenerate
via `npm run generate-docs`, don't hand-edit); if it's still open, that's a
real, reportable documentation gap in its own right — a consumer surprised by
bundle size has no doc telling them why, or that fixing it means editing
`registerThemeSlices.ts` after vendoring.

## Reporting discipline

Match `owasp-review`'s standard:
- Quote the actual file:line for every finding.
- State concretely what a consumer would experience (e.g. "importing only
  `<Button>` still bundles `DataTableSlice`, `ModalSlice`, and everything
  those transitively import").
- Explicitly separate "confirmed still present" (§1, re-verified) from "new
  finding" (§2/§3) from "docs gap" (§4) — don't collapse them into one
  generic summary.
- End with a status line per section (Confirmed present / Fixed since last
  audit / New finding / Clean) so a re-run's diff against a prior audit is
  legible at a glance.
