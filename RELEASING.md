# Cutting a toolcrib release

Split out of `AGENTS.md` (see that file's own "Cutting a release" section) since this whole sequence is invoked at exactly one specific, rare, maintainer-initiated moment — read this file in full only when the maintainer explicitly asks for a version bump, not as part of every session's standing context.

Only when the maintainer explicitly asks for a version bump — not something to do proactively alongside an unrelated change. **If they didn't name the exact target version, ask before starting step 1** — don't infer a semver bump from commit history; the same "needs explicit go-ahead on that specific version" bar step 8 states for the tag applies from the start, not just at the irreversible step. `.github/workflows/release.yml` triggers on a pushed `v*` tag and does the actual build/package/publish; everything below is what has to be true *before* that tag gets pushed, since the workflow verifies the tag matches `package.json` and will fail the whole release if the two disagree.

1. **Bump the root `package.json` `"version"` field only** — never `cli/package.json`'s or `mcp/package.json`'s; both are independently-versioned, independently-published packages, unrelated to the toolkit's version.
2. **Regenerate, don't hand-edit, everything version-derived**: `npm run generate-manifest && npm run generate-docs && npm run generate-index`.
3. **Verify for real before tagging**: `npm test` (root), `npx tsc --noEmit`, `cd cli && npm test`, then `npm run check-manifest`/`check-docs`/`check-index`. Also run `GITHUB_TOKEN=$(gh auth token) npm run generate-security-advisories`; commit the diff if it produced one.
4. **Re-check current source against `.plans/archive/toolcrib-defect-pindown-plan.md`'s taxonomy and `AGENTS.md`'s own anti-pattern entries, once, before tagging.** Full-repo read, not per-file: skim the plan's six taxonomy classes and `AGENTS.md`'s anti-pattern write-ups, then spot-check recent changes against each.
5. **Run the three security/accessibility/CI-workflow audit skills before tagging: `owasp-review`, `aria-compliance-review`, `actions-injection-review`.** In Claude Code, invoke each directly; on a tool that can't load a Claude Code skill, read `.claude/skills/<name>/SKILL.md` directly instead. Fix or file an issue for anything a pass finds before the tag goes out.
6. **Re-verify against the real consumer apps `feed-farmer-pwa` and `founders-desk`.** Re-apply current `main` into each (`toolcrib merge` against their vendored copy, or a fresh `toolcrib init` diffed against their current state) and run each app's own `tsc`/test suite. Fix any real failure before tagging, not after.
7. **Commit, PR, merge to `main` via the standard `WORKFLOW.md` sequence — then tag, not before.** Once merged: `git checkout main && git pull --ff-only` before tagging, so the tag points at a commit whose `package.json` version already matches, that has already gone through this repo's full CI.
8. **Tag and push**: `git tag -a vX.Y.Z -m "vX.Y.Z" && git push origin vX.Y.Z`. Also triggers `screen-reader.yml`.
9. **Watch it through**: `gh run watch <run-id> --exit-status` (find the run via `gh run list --workflow=release.yml --limit 1`). Confirm the release exists: `gh release view vX.Y.Z`. Also check `screen-reader.yml`'s own run for this tag (`gh run list --workflow=screen-reader.yml --limit 1`) before considering the release done.
10. **Post a release-summary discussion under "Announcements" once confirmed** — distinct from `SESSION_SUMMARIES.md`'s per-checkpoint posts. Summarize `git log v<prev>..v<new> --oneline` as real prose ordered by impact (biggest first), not a mechanical commit list — see discussion #504 (v0.15.0) for the calibration this is aiming for. Post via `gh api graphql`'s `createDiscussion` mutation, body via `-F body=@path` (never inline `-f`). Cached node IDs: repository (`escape-llc/toolcrib`) `R_kgDOTwhGaA`; "Announcements" category `DIC_kwDOTwhGaM4DDQXw`.

**Steps 1-7 are local/reversible. Step 8 (the tag push) is the one irreversible, public action — never do it without the maintainer's explicit go-ahead on that specific version.** Step 10 doesn't need a separate go-ahead — post it by default once the release is confirmed.
