# Contributing to Toolcrib

This file is for whoever (human or AI) is working **on** this repo — adding components, fixing bugs, extending the CLI. If you're building an app that **uses** toolcrib, this is the wrong file: see `ai-docs/CORE.md` (always) plus `ai-docs/NEW_APP.md` or `ai-docs/REFACTOR_APP.md` (situational) instead — those ship to consumers and are the canonical rule set for using the toolkit, not for building it.

## What this is

`toolcrib` is a React component library designed specifically for AI code generation ("vibe coding") — an AI that's building a UI tends to hand-roll the same popups, slide-outs, and ad-hoc CSS over and over. Toolcrib exists to give it a structural toolkit instead: slot-based components, a strongly-typed event bus for cross-tree actions, an HSV-derived CSS-variable theme system, and a Zod-schema-driven form engine.

The toolkit itself (`src/theme`, `src/eventBus`, `src/observer`, `src/components/**`) is **not distributed as an npm package**. Consumers run `toolcrib init` (via the `toolcrib` CLI on npm, built from `cli/`), which vendors those directories plus `ai-docs/` directly into their own project as reviewable patches, then wires a `#toolcrib` subpath import (`package.json`'s `"imports"` field) to it. `src/` is *only* toolkit source — nothing else lives there.

`demo/` (`App.tsx`, `main.tsx`, `index.css`, `vite-env.d.ts`), the root `index.html`, and this file are this repo's own dev/demo harness and contributor instructions — they are **not** vendored, and never will be just by adding them to a directory that happens to get copied. `demo/` imports the toolkit exclusively via `import { ... } from '#toolcrib'` (the same alias, resolved locally to `./src/index.ts` by root `package.json`'s own `"imports"` field) — never a relative path into `src/`. This is deliberate, not a style preference: a relative import can reach right past the public barrel into an internal file, so the demo would keep working even if `src/index.ts` forgot to re-export something a real consumer needs. Going through `#toolcrib` means the demo breaks the same way a real consumer's build would the moment that happens — see `@barrelExport` below for how `src/index.ts` itself stays honest.

## Generalizing lessons in this file

Every rule below started as one specific bug in one specific file. Whoever adds the next one — human or AI, in this repo or in an external review session — should write it up as the *underlying pattern*, not just the component/prop where it happened to surface, and fold it into an existing entry if one already covers the same root cause rather than appending a disconnected new one. "A trailing `{...props}` spread silently overrides anything set before it" (below) is the model to follow: it was found once, in one place, then found again in a completely different component months later, and because the entry was written at the level of the mechanism rather than the instance, it was fast to recognize the second occurrence as the same rule rather than a new bug needing its own separate write-up. The `typescript` pin at the bottom of this file is another example — it doesn't just say "don't upgrade," it says exactly why, so the next person evaluating an upgrade has the actual constraint instead of a bare prohibition.

This is also the concrete reason external review sessions like the one this file's currently-newest entries came from are worth deferring a release for: nothing in a single generation pass forces a check for "does this new code repeat a mistake already found and written up elsewhere," and nothing in this repo's CI checks that either — it's read-and-recognize, not automated. A session with room to read the whole codebase at once, cross-reference components against each other and against this file, and write actual regression tests catches exactly the class of thing that's invisible from inside any single generation turn. Feed what it finds back into this file at the general level, not the specific one, so the next pass — automated or not — has a better chance of recognizing the pattern before it has to be found a third time.

`SESSION_SUMMARIES.md` is the other half of this same feedback loop, aimed outward instead of in: a per-checkpoint prompt for posting a short, honest writeup (including friction) of a contributor session to this repo's own GitHub Discussions, rather than folding everything into this file's cumulative record.

That loop was one-directional until 2026-08-31 — plenty of guidance on *posting* a session's friction to Discussions, nothing telling the *next* session to actually go read what's already there before starting work. **Before starting anything beyond a trivial/mechanical change, check the last several posts under the "AI Session Summaries" Discussions category.** A gap already found and reported once (a component's real friction point, a bug that needed a non-obvious fix) shouldn't have to be independently rediscovered from scratch by the next session just because nothing prompted a look first — the same root problem this whole section already argues against for in-repo lessons, just aimed at the other half of the loop. Query it directly rather than browsing the web UI, using the same cached IDs `SESSION_SUMMARIES.md` documents for posting:

```
gh api graphql -f query='
query {
  repository(owner: "escape-llc", name: "toolcrib") {
    discussions(categoryId: "DIC_kwDOTwhGaM4DDiVO", first: 10, orderBy: {field: CREATED_AT, direction: DESC}) {
      nodes { title url createdAt }
    }
  }

```

Skim titles/dates for relevance to the task at hand, then fetch a specific one's full body (`bodyText` in place of `title url createdAt` above, or `gh api graphql -f query='query{ node(id:"..."){ ... on Discussion { bodyText } } }'` with that discussion's own node id) only for the ones that look relevant — reading all of them up front doesn't scale as the category grows, and most won't bear on any given task.

Two related process notes, both found doing exactly the kind of full-repo pass this section already argues for: **a hand-authored file checklist for a wide rename under-enumerates, reliably.** Renaming `SlideOut`→`Drawer` (commit `d11308e`) followed a hand-off doc's own file list faithfully, then a repo-wide grep at the very end still turned up six more real occurrences it hadn't named — `demo/App.tsx` (a functional consumer, not just prose), a generated-docs lookup table, e2e specs, this file. None were individually surprising, but the checklist itself wasn't a complete acceptance bar — the final grep was. Treat a repo-wide search as the actual gate for any rename this wide, not the checklist that preceded it.

**A planning document's own specific, checkable claims (a field count, a file path, a proposed name) need independent verification before acting on them, even when its overall reasoning is sound.** This recurred across several hand-off-doc-driven sessions in a row (a slice-count off by one, a wrong build-pipeline file path, a proposed CLI flag name that didn't match the codebase's own established term) — different documents, same shape every time: strong architecture, an unverified specific fact sitting right next to it. Applies equally to any `.plans/*.md` document (including this repo's own defect pin-down plan) — verify a plan's concrete, checkable claims against the current source before implementing from it, the same discipline this file already asks for regarding its own bug write-ups.

## Dev machine is Windows — use PowerShell, not Bash

The primary dev machine for this repo runs Windows, and its `Bash` tool is a minimal git-bash without coreutils — `ls`, `grep`, `rm`, `find`, `head`, `tail`, `sleep`, and even `node`/`npm` are missing or unreliable there, confirmed repeatedly by real failures, not assumption. **Run shell commands (`npm`, `node`, `git`, etc.) via the PowerShell tool, not Bash.** Use the dedicated file tools (Read/Write/Edit/Glob/Grep) instead of either shell for file operations wherever possible — they aren't affected by this at all.

PowerShell-specific gotchas hit in practice:
- `Start-Process -FilePath "npm"` fails **silently** (no process, no error) — Windows needs the actual executable name, `npm.cmd`, not the bare command a normal shell would resolve via PATHEXT.
- The console can mangle non-ASCII characters (em dashes, etc.) on read-back even when the file on disk is correct UTF-8 — if a file's content looks corrupted after `Get-Content`, verify with `[System.IO.File]::ReadAllText(path, [System.Text.Encoding]::UTF8)` before assuming the file itself is broken.
- The working directory does not reliably persist between separate tool calls the way a single interactive shell session would — pass an explicit `cd`/path in each command rather than relying on a previous `cd` still being in effect.
- `.gitattributes` (`* text=auto eol=lf`) normalizes line endings repo-wide, but it only affects the *index* going forward — a file already checked out with stale CRLF (from before `.gitattributes` existed, or from `core.autocrlf=true`) stays CRLF on disk indefinitely; `git status`/`git checkout HEAD -- <file>` both silently no-op on it, since autocrlf-aware comparison treats the CRLF working copy and the LF blob as equivalent. Found for real while investigating an unrelated `npm publish` warning about `cli/src/index.js`'s `bin` entry — that warning turned out to be a harmless, unrelated cosmetic path normalization (npm stripping a redundant leading `./`), but the file's shebang line genuinely did still have stale CRLF from before `.gitattributes` existed, which would break real execution on Linux/Mac (`#!/usr/bin/env node\r` resolves to a nonexistent `node\r` interpreter). `git checkout HEAD -- cli/src/index.js` alone did nothing to fix it. The actual fix is deleting the file first so there's nothing to short-circuit against, then re-checking it out: `rm <file> && git checkout HEAD -- <file>`. Verify with a real byte-level check (`buffer.includes(0x0d)` in Node, not `git status`) before trusting it's fixed — and don't assume a CRLF-adjacent error message is actually about CRLF; verify the real cause before "fixing" it.

## Core rules

The actual component/theme/event-bus rules (no prop-drilling, HSV-only color, `rem` units, anti-patterns) live in `ai-docs/CORE.md` — that file is the single source of truth, read by consumers and shipped as-is. Don't duplicate those rules here; if you change one, change it there and keep this file's references in sync.

## `<Form>`'s `onSubmit`/`form:submitted` must receive the schema's parsed output, not raw field state

`FormContext.tsx`'s `handleSubmit` computes validity via `schema.safeParse(values)` and then must hand `onSubmit` (and the `form:submitted` event) that same call's `result.data` — never the raw `values` state object directly. A version that passed `values` (the previous implementation) validated correctly but silently discarded whatever the schema's own `z.coerce.*`/`.transform()` produced, so `FormProps.onSubmit`'s declared type (`z.infer<typeof schema>`, e.g. a real `number` for `z.coerce.number()`) didn't match what actually arrived at runtime (still the original string). Found for real building the Founder's Desk example app: a `.toFixed()` call on what its own schema's type said was already a `number` crashed `<DataTable>`, because the value was still the submitted string.

Every field control (`<Input>`, `<Select>`, etc.) always stores a raw value in `values` regardless of schema — that's correct and unrelated; it's specifically the one-time hand-off at submission (and nowhere else) that has to route through the schema's parsed result. `parseValues()` (the internal helper `validateValues` was renamed to, since it now returns `{ errors, data }` instead of just errors) is the single place this is computed — any future change to `handleSubmit` that reads `values` directly instead of destructuring `data` from `parseValues(values)` is reintroducing this exact bug. `Form.test.tsx`'s `"regression: onSubmit receives the schema's parsed output, not raw field strings"` suite exists to catch that regression directly.

## Documenting a component for the manifest

`ai-docs/component-manifest.json` is **generated**, not hand-edited — `node scripts/generate-manifest.js --write` (or `npm run generate-manifest`) rebuilds it from JSDoc directly on component source via the TypeScript Compiler API. `npm run check-manifest` validates there's no drift, and CI runs it on every release; a component with missing/wrong tags either doesn't show up at all or fails the build, silently or loudly depending on which mistake you make below.

**A component needs an `@manifest` tag to appear at all.** Put it in a JSDoc block directly above the component's `export const X: React.FC<...> = ...` (or `export function X(...)`) declaration — **not** on the Props interface. Some props interfaces are shared by more than one component (`VStack`/`HStack` both use `StackProps`), and each needs its own description, so description is a property of the component declaration, never of the prop shape:

```tsx
/** @manifest Slot-based container with automatic layout domain corner squaring */
export const Card: React.FC<CardProps> & { Header: ...; Content: ...; } = (...) => { ... };
```

**Props** are read from the interface referenced by the component's `React.FC<...>` type argument (or, for generic function components like `Form`/`DataTable`, the first parameter's type). Per property:
- Plain JSDoc prose above the property becomes its `description`.
- An `@default <value>` tag becomes its `default`.
- No `?` on the property (i.e. required in TypeScript) automatically becomes `"required": true` in the manifest — nothing to tag, just don't mark it optional if it isn't.
- `children` is never listed — implicit on every component, consistent with the manifest's existing style.

```tsx
export interface CardProps {
  /**
   * Layout mode. `'auto'` enables flex fill + corner squaring.
   * @default 'default'
   */
  layout?: 'default' | 'auto';
}
```

**Slots** (`Card.Header`, `Modal.Body`, etc.) are discovered automatically by scanning the component's file for `ComponentName.SlotName = ...` assignments — no tag needed. Standard React statics assigned the same way (`Component.displayName = ...`) are excluded automatically; don't add new ones to that exclusion list casually if you're not sure they aren't a real slot.

**`@manifestCategory <name>` is required, not optional** — one of `Layout Primitives`, `Containers`, `Overlays`, `Data Display`, `Form Controls` (`VALID_CATEGORIES` in `scripts/lib/extract.js`). Generation fails outright (both `--check` and `--write`) if a `@manifest`-tagged component is missing it or uses a value outside that set — it's what groups components into `ai-docs/CORE.md`'s generated Component Reference tables (§4), so an uncategorized component would otherwise fall out of that doc's tables silently.

**Two more tags for facts that aren't mechanically derivable:**
- `@manifestConstraints <text>` — a structural requirement the type system can't express (e.g. Splitter's `@manifestConstraints Requires exactly 2 children`).
- `@manifestChildren <Comma, Separated, Names>` — a curated "commonly used together" list, e.g. Form's child form controls. This is a judgment call about typical usage, not a property of the source, so it has to be authored, not inferred.

**Custom/grouped import lines** (Form's import bundles ten related exports in one statement, not just `Form` itself) aren't derived either — they're a `MANUAL_IMPORT_OVERRIDES` entry at the top of `scripts/generate-manifest.js`. Add an entry there if a new component needs the same treatment; every other component defaults to `import { X } from '#toolcrib'`.

**Event bus channels** are read from the `AIEventMap` interface in `src/eventBus/eventBus.ts` — add a new event there and it appears in the manifest automatically, "payload" being that property's literal TS type. Keep new payload types to one line; a multi-line type with inline comments (like `theme:changed`'s) still works but gets whitespace-collapsed and comment-stripped in the generated output, so writing it compactly to begin with is just less to translate mentally.

**Event bus helper methods** (`aiBus.openModal(...)` etc.) are read from `AIEventBus`'s methods, excluding `on`/`off`/`emit` themselves. "emits" is read from the first `this.emit('event:name', ...)` call in the method body. If a method returns something worth documenting (like `showToast` returning the toast id), add `@manifestReturns <description>` to its JSDoc — otherwise `returns` is simply omitted.

**After any of the above:** run `npm run generate-manifest`, review the diff, commit it alongside your source change. Don't hand-edit `component-manifest.json` directly — the next run will silently overwrite it, and CI will catch the drift anyway. The same run also regenerates `ai-docs/manifest/<slug>.json` — a per-`@manifestCategory` slice of the same `components`/`$defs` data, letting an agent working in one category load only that category's detail instead of the full manifest. It's generated by the exact same command/`--check` as the root manifest, not a separate manually-maintained layer — never hand-edit those either.

**`ai-docs/CORE.md` is also generated, not hand-edited** — `node scripts/generate-docs.js --write` (or `npm run generate-docs`) renders `ai-docs/templates/CORE.md.hbs` against the same source-derived data as the manifest (shared via `scripts/lib/extract.js`, so the two can't disagree with each other). This exists because CORE.md's hand-written tables had already drifted before this pipeline did — missing 9 of 32 real event channels and 4 of 20 real components at the time it was built. `npm run check-docs` (or `node scripts/generate-docs.js --check`) validates there's no drift, same contract as `check-manifest`; CI runs both. If a source change should change CORE.md's *generated* sections (Component Reference, Z-Index table, Theme Slices list, Event Bus payload reference), regenerate — don't hand-edit the committed file. If it should change CORE.md's *static* prose (Root Setup, Core Principles, Anti-Patterns, the escape-hatches/overrides sections, code samples), edit `CORE.md.hbs` directly, then regenerate.

**`generate-docs.js` also renders `llms.txt`/`llms-full.txt` at the repo root** — same command, same `--check`/`--write` contract, same run (it's one more pair of entries in that script's own `targets` list, not a separate generator). These are a different audience than everything else `ai-docs/` contains: `ai-docs/` is aimed at an AI that has *already* vendored toolcrib into a consumer app and needs usage guidance; `llms.txt` is aimed at an LLM encountering the toolcrib project itself for the first time (a search, a GitHub browse, an agent doing research) — pre-adoption discovery, not post-adoption reference. `llms.txt` follows the [llmstxt.org](https://llmstxt.org/) spec (H1, one blockquote summary, H2-sectioned link lists, a specially-named `## Optional` section for links droppable when context is limited) via `ai-docs/templates/llms-txt.hbs`, with a handful of source-derived facts (component count, category list, event channel count) interpolated in so the summary can't silently drift the way `README.md`'s own hand-typed component count already has (confirmed directly while building this: `README.md` says "68 production components," the real count is 69 — a pre-existing drift in the repo's one hand-maintained file, not something this pipeline introduced or has fixed yet). `llms-full.txt` has no template of its own — it's the community-convention "everything inlined in one file" companion (not part of the formal spec), built by pure concatenation of `README.md` + that run's own `CORE.md` render + `NEW_APP.md` + `REFACTOR_APP.md`, each section marked with a `<!-- ===== file.md ===== -->` label (a bare `---` would be ambiguous with CORE.md's own internal section dividers). Neither file is vendored to consumers via the CLI — like `AGENTS.md`/`CONTRIBUTING.md`/`SESSION_SUMMARIES.md`, they describe this repo, not the toolkit source `toolcrib init` copies.

When authoring new `.hbs` content — a worked example under `ai-docs/templates/examples/`, or an addition to `CORE.md.hbs` itself — remember Handlebars' `noEscape: true` (set for these templates) only disables HTML-escaping, it does **not** stop `{{...}}` from being parsed as a mustache expression. Literal JSX double-curly syntax in example prose (`overrides={{ subtheme: 'success' }}`) breaks generation with a "Missing helper" error unless escaped as `\{{...}}` — grep the existing templates for `\{{` to find the established use sites before assuming this is a new problem.

**`mcp/`'s parsing code has no automated check keeping it in sync with the ai-docs shape — check it by hand whenever that shape changes.** `check-manifest`/`check-docs`/`check-index` only guard the generated *artifacts* (`component-manifest.json`, `CORE.md`, `src/index.ts`) against drift from source — nothing guards the separate `toolcrib-mcp` package (`mcp/src/lib/manifestIndex.js`, `coreDoc.js`, `examples.js`), which reads those generated artifacts' *shape* directly and has its own independent release cadence (see `mcp/CONTRIBUTING.md`). A change to any of the following needs a corresponding look at `mcp/src/lib/`, since nothing else will catch a mismatch until a real MCP tool call returns wrong or missing data at runtime:
- A top-level `component-manifest.json` key added, renamed, or removed (`themeSystem`, `zIndexScale`, `eventBus`, `components`) — `manifestIndex.js` reads all four by name.
- `eventBus`'s own shape (`channels`/`helperMethods` as arrays of `{name, payload}`/strings) — `getEventChannels()` assumes this exact structure.
- A per-component field renamed (`category`, `description`, `slots`, `props`) — `searchComponents()`'s `fuse.js` index keys on `name`/`description`/`category` specifically.
- `CORE.md`'s heading convention (`##`/`###` only, in `ai-docs/CORE.md.hbs`) — `coreDoc.js`'s section splitter is a plain regex on that pattern, not a Markdown parser.
- `ai-docs/examples/` file naming or the "first non-heading line is the description" convention — `examples.js` assumes both.

This manual check has a partial runtime backstop, not a substitute for it: `mcp/src/lib/compatibility.js`'s `COMPATIBLE_RANGE` names the toolcrib version range a given `toolcrib-mcp` release has actually been built and tested against (a semver range, checked against `.toolcrib-lock.json`'s version at startup). A vendored version outside that range surfaces a `compatibilityWarning` in `get_install_info`'s response and a one-line stderr message at server startup — a warning, not a hard failure, since an ai-docs shape change is often additive and an untested newer version may still parse fine. This only tells you *that* a version is unverified, never *whether* the shape actually changed — after checking `mcp/src/lib/` against a new ai-docs shape per the bullets above, widen `COMPATIBLE_RANGE` to include the newly-verified version as part of that same change.

## Keeping `src/index.ts` (the public `#toolcrib` barrel) in sync

`src/index.ts` is also generated, not hand-edited — `node scripts/generate-index.js --write` (or `npm run generate-index`) rebuilds it by scanning every file under `src/theme`, `src/eventBus`, `src/observer`, and `src/components/**` for exported declarations tagged `@manifest` or `@barrelExport`, and re-exporting the *whole file* (`export * from './path'`) for any that qualify. `npm run check-index` validates there's no drift; CI runs it alongside `check-manifest`/`check-docs`. This exists because the hand-maintained version drifted for real — an audit while separating the demo app from the toolkit found `Content`, `DataTableSlice`, and `useSliceOverrides` silently missing, each shipped to every consumer as a vendored file but literally unimportable via `#toolcrib`.

**A component's `@manifest` tag already counts** — nothing extra to add. For everything else meant to be public (a hook, a `ThemeSlice` definition, a context's exported types, a shared utility), tag one exported declaration in the file with `@barrelExport`:

```ts
/** @barrelExport */
export interface TableSliceState {
  density: TableDensity;
  ...
}
```

One tagged declaration is enough — the whole file gets re-exported alongside it, so a component's own Props interface doesn't need its own tag once the component itself is tagged. This is opt-in by design, not opt-out: nothing lands in the public API surface without an explicit marker, matching `@manifestCategory`'s own "required, not inferred" philosophy above. If you add a new file under one of the vendored directories and forget to tag anything in it, `check-index` simply won't include it — no error, just silence, so if something you just added isn't reachable via `#toolcrib`, this is the first thing to check.

**After any of the above:** run `npm run generate-index`, review the diff, commit it alongside your source change — same discipline as `generate-manifest`/`generate-docs`.

## Theme overrides — no component accepts `style`/`className`

Every component's Props interface extends `StyleFree<...>` or `StyleFreeAttributes<T>` (`src/theme/safeProps.ts`) instead of a raw `HTMLAttributes<T>`/`ButtonHTMLAttributes<T>`/etc. — extending the raw attributes type silently reintroduces `style`/`className` regardless of whether the interface redeclares them itself, so deleting the interface's own `style?:`/`className?:` lines is not sufficient on its own. If a component genuinely has nothing else to add, `StyleFreeAttributes<HTMLDivElement>` alone is fine.

Per-instance visual control goes through an `overrides` prop instead, resolved via a four-layer hierarchy: global theme → per-component-type `ThemeSlice` default → contextual domain → this specific instance. Concretely:
- A component with a registered `ThemeSlice` (`src/theme/slice.ts` — e.g. `CardSlice.ts`, `TabSlice.ts`) exposes `overrides?: Partial<SliceState> & { subtheme?: SubthemeName }` and calls `useSliceOverrides(TheSlice, overrides)` (`src/theme/useSliceOverrides.ts`) to get back `{ vars, subtheme }` — spread `vars` into the component's own root `style` (after its other properties, so it wins) and pass `subtheme` to `resolveSubtheme()` (`src/theme/subtheme.ts`) if the component has any subtheme-reactive styling.
- A component with no slice but simple subtheme support (e.g. `Button`) calls the lighter `useResolvedSubtheme(instanceValue)` directly instead.
- Add `fieldVars` to a slice (`{ fieldName: ['--css-var-1', '--css-var-2'] }`) whenever you add one — `getSparseVariables()` uses it to emit only the CSS variables a partial override actually touches, so an instance override doesn't shadow the global Theme Editor state for fields it never mentioned. A slice without `fieldVars` still works, just emits its full result (correct, just over-shadowing) — add it when convenient, not as a hard blocker.
- `<StyleDomainProvider subtheme="...">` (`src/theme/StyleDomainContext.tsx`) lets a whole subtree default to a subtheme without passing `overrides.subtheme` on every descendant — the instance's own value still wins if set. It's Context-based, not CSS-variable inheritance, specifically because Modal/Popup/Drawer all render through a portal, and CSS custom properties only cascade through the real DOM tree, not the React tree.
- `LayoutDomainContext`/`useCornerSquaring` (`src/components/Splitter/LayoutDomainContext.tsx`) is the equivalent mechanism for spatial/containment concerns (which corners a component should square off inside a `<Splitter>`) rather than semantic ones — same shape, different axis.

**General rule: a trailing `{...props}` spread silently overrides anything set before it — including a value you computed on purpose.** This has now bitten the codebase twice, in two structurally identical but superficially different ways, which is exactly why the rule belongs here at the general level rather than as two disconnected bug notes:

- *Instance 1 (the original case this rule was written from):* `Splitter.Panel`, `UIGroup`, and `Popup`'s/`Drawer`'s trigger cloning used to coordinate corner radius/sizing with a child via a `cloneElement`-injected `style` prop. It silently stopped working once the child's own computed `style` (declared after its own `{...props}` spread) started winning every render — the injected value never had a chance to apply. Prefer, in order: (1) the child consults `useCornerSquaring`/`useStyleDomain` itself if it's a toolcrib component with domain/context access; (2) a small typed prop the child explicitly declares and applies itself, e.g. `Button`'s `squareCorners?: SquareCornerOption` consumed via the shared `resolveSquareCorners()`; (3) for a visual effect that has to apply uniformly to *any* child regardless of type — including a plain DOM element, which can't call hooks — an injected global stylesheet scoped by a wrapper `className`/`data-*` attribute (see `UIGroup`'s corner-merging CSS) is more robust than per-child style injection and doesn't care whether the child accepts a `style` prop at all.
- *Instance 2 (found in an external review session, not caught by any test at the time):* `SubmitButton` computed `disabled={isSubmitting || props.disabled}` and then spread `{...props}` *after* it. Any consumer passing their own `disabled` at all — e.g. the very natural `<SubmitButton disabled={!isValid}>` to gate submission on form validity — had that original value silently re-applied by the trailing spread, discarding the `isSubmitting ||` guard the instant it ran. The button stopped showing disabled during the actual submit, exactly when double-submit protection mattered most. Fix: reorder so `{...props}` comes first and the computed value that must win is applied after it — `<Button type="submit" {...props} disabled={isSubmitting || props.disabled}>`.

**The general check, for any component that both spreads `{...props}` (or `cloneElement`s a child) and computes a value from other props/state/context:** does anything computed need to win over what a consumer might pass under the same prop name? If so, that computed application must come *after* the spread, never before — regardless of whether today's consumer happens to pass that prop. Don't reason about the common case only ("nobody usually passes `disabled` here") — the ordering has to be correct for the case where they do, since that's exactly when it matters.

If a component sets a shorthand CSS property (`borderRadius`) unconditionally and a longhand (`borderBottomLeftRadius`) only *sometimes* (e.g. gated on `squareCorners`), React warns "Removing a style property during rerender ... can lead to styling bugs" whenever that conditional toggles across renders — the fix is emitting all four corner longhands unconditionally (falling back to the shorthand's own value when not overridden) rather than mixing a shorthand with a sometimes-present longhand. See `Button`'s corner-radius computation for the pattern.

**A flex child inside a scrollable column needs `flex-shrink: 0`, or it silently gets crushed instead of scrolled to.** A flex item's default `flex-shrink: 1` means once combined content exceeds the space an ancestor gives it, the browser shrinks the shortest-resistance child down to a couple of pixels instead of letting the ancestor's own scroll region (which already exists, and already computes the correct `scrollHeight`) take over — no error, no warning, just a component that's correct in the DOM while looking empty or truncated on screen. Found in `TabStrip.Panel` (commit `cc37962`) via a real screenshot, not a failing test — jsdom has no layout engine and structurally cannot catch this class of bug (see `.plans/toolcrib-defect-pindown-plan.md` for the general pattern this is one instance of). `VStack` and any other flex-column container this codebase's layout primitives compose have the same shape; a scoped stylesheet rule targeting only that component's own direct children (`.ai-tabstrip-panel > * { flex-shrink: 0; }`) is the fix, not an inline style — a container can't set `style` on arbitrary consumer-supplied children.

**A non-focusable wrapper around a focusable descendant needs more than a plain `:focus-visible` rule — now fixed at the primitive, not per-instance.** `.ai-focus-ring`'s original rule was pure `:focus-visible` — it only ever matches the exact element it's applied to, so putting it on a non-focusable wrapper `<div>` around a real focusable child (`Combobox`'s own `<input>`, e.g.) drew no ring at all, ever. Confirmed directly (commit `508e935`): what looked like "the focus ring is there but buried/obscured" was actually "there is no focus ring, full stop." The first fix (that commit) added a separate `.ai-focus-ring-within` class with a `:focus-within` rule for this one shape — a correct but ad hoc, per-instance correction: the next component with this same shape still had to have the mistake independently found and manually fixed a second time, the same "found once vs. found forever" gap §7.1 already calls out for the `{...props}`-ordering rule.

Closed for good in `interactionStyles.ts`: `.ai-focus-ring` now matches `:focus-visible, :has(:focus-visible)` in one rule — the second branch catches "a descendant has keyboard focus" without the false-positive-on-mouse-click problem plain `:focus-within` has (which matches on *any* focus, defeating the entire point of using `:focus-visible` everywhere else in this file). A component author reaches for the same one class regardless of whether their component is itself focusable or wraps a focusable descendant, and it's correct either way — there's no second, similarly-named class to misapply or forget exists. `.ai-focus-ring-within` no longer exists; `Combobox.tsx` (its one real consumer) now uses plain `.ai-focus-ring`.

The same pass also fixed a second, unrelated gap in the same rule: the ring previously snapped on/off with `outline`'s shorthand toggling `outline-style` between `none`/`solid` at the exact moment `:focus-visible`/`:has(:focus-visible)` started matching — `outline-style` is a discrete keyword, not a continuously-interpolable value, so no `transition` on a later-added property could ever smooth that first appearance. The fix: declare the outline unconditionally (`outline-style: solid`, transparent colour) in a base rule, and transition only `outline-color` — the standard technique for a fading, rather than snapping, focus indicator. Reuses `--ai-transition-duration-fast`/`--ai-transition-easing` (`animation.tsx`), the same tokens `:active`'s `--ai-active-transform` already reuses, so the fade automatically respects the Motion/Physics preset and `reducedMotion` setting with no separate opt-out of its own.

**A theme slice emitting a CSS variable for a genuinely-inherited property (`color`, `line-height`, ...) is a silent trap if nothing actually applies it at `:root`.** Nothing in this file flagged "is this CSS custom property computed-and-emitted but never consumed anywhere" as its own category of bug until it was asked about directly (commit `6831d4c`) — `demo/index.css` had accumulated hardcoded literals (`color: #111827`, `line-height: 1.5`) that happened to already match the theme's own current defaults, so nothing looked broken, but they'd silently diverge the instant a consumer changed either value in the Theme Editor, since a hardcoded rule never tracks a variable it doesn't reference. Worth a standing check whenever a new slice introduces a CSS variable for an inherited property: confirm something (usually a `:root`-scoped rule) actually reads it, not just that the variable exists.

**A shared row/field helper should own its own id generation internally, not lean on every call site to remember to supply one.** `ThemeEditor`'s `FieldRow` (~50 call sites of an unassociated label/`<Select>` pair, fixed in commit `1b17cd3`) is exactly the shape of accessibility bug that's easy to introduce once and then copy-paste 50 times over. A single `useId()` call inside the shared helper itself closes the whole class at once; asking every call site to remember its own association doesn't scale, and this one went unnoticed until a full manual ARIA audit found it — there's no mechanical shortcut for "does this component have an unassociated label" the way `check-manifest` catches a missing `@manifest` tag.

**Never reference `process.env` (or any other single bundler's ambient global) directly in vendored source — it type-checks fine here and fails the moment it's vendored into a consumer project that never opted into that bundler's types.** `RouterAdapterContext.tsx`'s dev-only warning used a bare `process.env.NODE_ENV !== 'production'` check. This repo's own dev environment happens to have `@types/node` installed (a transitive dependency of tooling elsewhere), so it silently type-checked here and the mistake shipped for at least one release before an external head-to-head comparison against a competing library caught it — that same competing library made the identical mistake independently, in five separate files, which is what surfaced the pattern clearly enough to name it here. `theme/safeProps.ts` already has the correct, general-purpose answer to this exact problem: `isDevBuild()` reads `import.meta.env.DEV` first, then falls back to `process.env.NODE_ENV` — both accessed through an `unknown`-cast `globalThis` lookup specifically so neither Vite's nor Node's ambient types need to be present for the *file itself* to compile, only for the corresponding runtime value to actually exist at whichever bundler the consumer happens to use. Use `isDevBuild()` for any future dev-only branch; never read `process`/`import.meta.env` directly outside `safeProps.ts` itself. A `no-restricted-globals` ESLint rule on `process` now enforces this at lint time (`scripts/eslint.config.js`) — it's scope-based, so it correctly leaves `safeProps.ts`'s own `globalThis.process` property access alone (that's a property name, never a reference to the global) while catching any new bare `process.env` reference anywhere else in `src/`.

**A component built on a third-party primitive can silently omit a standard, spec-recommended ARIA attribute the primitive itself never sets — and none of this repo's own checks are structurally positioned to catch that class of gap.** `Modal`/`AlertDialog` never declared `aria-modal="true"` themselves, relying entirely on `@radix-ui/react-dialog`'s `Content` (which `AlertDialog` is also built on internally) to provide it — but that package's own source never sets `aria-modal` anywhere; it achieves real modal *behavior* a different way (the `aria-hidden` package's `hideOthers()`, applied to DOM siblings) without ever declaring the attribute the WAI-ARIA Dialog (Modal) pattern recommends. Found via the same external comparison session, and instructive for *why* nothing here had already caught it: `aria-modal` is optional per the ARIA spec, not required for `role="dialog"` to validate, so axe-core's `aria-required-attr` rule structurally cannot flag its absence (this is exactly the category `aria-compliance-review` exists to cover, and Modal/AlertDialog simply hadn't been in a pass's scope yet) — and because Radix's `aria-hidden`-on-siblings approach still delivers working modal behavior, nothing about the dialog looked or behaved broken in any manual or automated interaction test either. Fixed by passing `aria-modal="true"` explicitly on both components' `Content` (`Overlay.test.tsx`/`AlertDialog.test.tsx` now assert on it directly, since nothing else ever will). Worth a standing check whenever wrapping a third-party accessibility primitive: confirm the *specific* attributes the relevant ARIA pattern calls for are actually present in the rendered DOM, not just that the primitive is "accessible" in general — a primitive can legitimately achieve equivalent behavior through a different mechanism while still leaving a spec-declared attribute absent.

## Distribution & path handling

The CLI (`cli/`) generates git patches for a consumer's project via `PendingChanges` (`cli/src/lib/patches.js`). Every relative path that ends up in a patch header **must** be forward-slash, unconditionally — `git apply` rejects backslash-separated paths outright, and this is not hypothetical: an early version of this exact mechanism broke `git apply` for every nested vendored file on Windows, invisibly, because CI only runs on Linux. Use `joinPatchPath()` from `lib/patches.js` for any new relPath construction; never `path.join()` for a string that becomes part of a patch, even if its inputs already look like they use `/` — `path.join()` normalizes to the platform separator regardless. `PendingChanges.propose()` itself also normalizes as a last-mile backstop, but don't rely on that as the only defense.

**The identical rule applies to zip archive entries, confirmed the same way (real byte-level inspection, not assumed).** `scripts/lib/zipPack.js` (shared by `package-release.js`/`package-tests-release.js`) builds `toolcrib.zip` entry-by-entry on Windows rather than using `Compress-Archive`/`ZipFile.CreateFromDirectory` — both were confirmed, at the raw byte level, to store literal backslashes for every entry when run on Windows, and passing a forward-slash *source* path to either makes no difference (the separator comes from .NET's own internal directory-walk, not the input path's style). A zip built that way would extract as a broken flat file (`ai-docs\CORE.md` as one literal filename) on any consumer using real Linux/Mac `unzip`, which treats a stored backslash as a filename character, not a path separator. If you ever touch zip-building code, verify entry names at the byte level (read the local file header's filename bytes directly) rather than trusting a library's own display of them back — `ZipArchiveEntry.FullName`, read back via .NET itself, looked identical whether the underlying bytes were forward-slash or backslash, masking the real on-disk representation.

The same real-Windows-run also found: fence regexes (`cli/src/lib/fences.js`, used for the managed-block system below) must tolerate `\r?\n`, not just `\n` — `git apply` writes CRLF whenever `core.autocrlf=true`, a common Windows Git default. And `readJsonIfExists`/`readJSON` (`cli/src/lib/project.js`, `release.js`) strip a UTF-8 BOM before `JSON.parse()` — Node's `fs` never does this itself, and it breaks parsing outright on a BOM'd `package.json`/`tsconfig.json`.

**`readTextIfExists` (`cli/src/lib/project.js`) deliberately does NOT strip a BOM, unlike `readJsonIfExists` — the opposite of what you'd guess from the paragraph above, and a real, previously-shipped bug when it got that wrong.** Every call site of `readTextIfExists` feeds `changes.propose()`'s "current" argument, which becomes the literal "before" context in a real patch that `git apply` later matches byte-for-byte against the real file on disk. An earlier version stripped the BOM there too — reasonable-looking, symmetric with `readJsonIfExists`, and wrong: it made the patch's "before" text no longer match the real (BOM'd) file, so `git apply` rejected it on the very first line ("patch does not apply") and the patch was silently discarded, every time, on a project whose `package.json` happened to carry a BOM (PowerShell's `Out-File`/`>` redirection adds one by default — a realistic, not contrived, way for a Windows user to end up with one). Found via `cli/integration-test/run-windows-integration.mjs`, not reasoned out in advance; a permanent regression test now lives in `cli/test/git.test.js` (real `git apply`, not mocked). The general lesson: when a function's real purpose is "represent what's actually on disk so a byte-level diff/patch mechanism can match it," normalizing away *anything* — a BOM, a line ending, a separator — is a bug even if it looks like harmless cleanup, because the other side of that comparison (a real `git apply`, a real `unzip`) never normalizes anything itself.

If you touch CLI path-handling or file-reading code, prefer testing it against a real `init`/`apply`/`doctor` run over a dummy project (see `cli/CONTRIBUTING.md`'s integration-test section) — the unit tests cover the pure-logic modules, but this exact class of bug is invisible to them by construction (Linux dev/CI environments don't reproduce it). This is now also a standing, automated CI job (`windows-integration` in `ci.yml`, via `cli/integration-test/run-windows-integration.mjs`) — a real `toolcrib init`/`apply`/`doctor` against a real mock GitHub server, with a deliberately BOM-prefixed `package.json`, on a real `windows-latest` runner — not just a manual procedure to remember to run.

### Managed fence blocks

`toolcrib init`/`merge` write ai-docs content into a consumer's own `AGENTS.md` (and detect drift there on `doctor`), wrapped in `<!-- toolcrib:managed:<id>:start version=X.Y.Z -->` / `:end` HTML-comment fences (`cli/src/lib/fences.js`, applied to Markdown via `lib/managedDocs.js` and to `.gitignore` via the `#`-comment style). The same generic primitive supports a `js` (`//`) comment style for a future feature that patches consumer source files directly — nothing uses it yet. Content inside a fence carries an auto-inserted "do not edit by hand" banner and is meant to be regenerated by `toolcrib merge`, not hand-edited — unlike vendored component source, which is explicitly meant to be forked/customized freely.

### A new component/hook that uses hooks, context, or browser APIs needs `'use client'` as its literal first line

Confirmed via a real, from-scratch reproduction (see `.plans/toolcrib-use-client-affected-files.md`): a fresh Next.js App Router project, `toolcrib init`'d at a real release, with a default (Server Component) page importing `Modal`, failed `next build` with errors across vendored files — every file that itself calls a React hook, `createContext`, or a browser-only API, or imports another vendored file that does, needs `'use client'` as the literal first line (before any imports; before or after an existing leading comment block is fine, since directive-prologue recognition ignores comments) or Next.js refuses to build it into a Server Component's module graph at all.

**The true scope was 79 files, not the 51 first identified — the first pass undercounted because of two distinct, now-understood gaps.** The original 51-file list was built from tracing one specific import (`Modal` only) by hand; that missed the fact that importing *anything* through the `#toolcrib` barrel (`src/index.ts`'s `export * from` re-exports) pulls Next's RSC-boundary analysis across the **entire** re-exported graph, not just the one import's own transitive chain — so a second real build (importing `ThemeProvider` too) immediately surfaced files the first pass never touched. A follow-up whole-tree scan closed that gap mechanically, but its first version matched only an *enumerated* list of React's built-in hook names (`useState`, `useEffect`, ...) and missed files that call a **custom** hook by naming convention only (`Calendar.tsx` calling `useSliceOverrides`, which itself wraps `useContext`) — found by bisecting the real barrel against a real `next build` down to that one file, not by reading the scan output. Rewriting the scan as a general `\buse[A-Z]\w*\s*\(` pattern (any `use`-prefixed call, not an enumerated list) found the rest. A textual match still isn't sufficient on its own, either: the same scan flagged `eventBus/eventBus.ts` for a `useLocaleStrings()` mention that turned out to be inside a JSDoc comment, not executable code — confirmed by checking the actual matched line before applying the fix.

**The standing lesson: a hand-traced import list and a keyword-based scan are both real progress but neither is ground truth — a real `next build` against the actual barrel is.** Whenever this class of check is redone (a new component added, a future doubt about coverage), scan the whole `src/` tree with the general hook-naming pattern *and* verify the result against a real Next.js App Router build importing multiple entry points through `#toolcrib`, not just one. This is a standing rule for *any new* component/hook/context file added to `src/`, not just the batch that was fixed: if it uses a React hook (built-in or custom), `createContext`, or a browser-only API (`document`, `window`, `ResizeObserver`, etc.) directly or transitively, it needs the directive too, or the exact same class of Next.js build failure reappears for the next consumer who hits it. There's no automated check for this yet (unlike `check-manifest`/`check-docs`/`check-index`) — a real Next.js App Router reproduction is what actually catches a missing one; a plain `tsc`/`vitest`/`vite build` run (this repo's own CI) cannot see it, since none of those understand or enforce React Server Component boundaries.

## Testing

Write tests for anything you add — pure `src/theme`/`src/eventBus` logic and component behavior go in `src/__tests__/`, CLI `lib/` functions go in `cli/test/`. Match the existing file's structure/conventions rather than inventing a new pattern. `npm test` (root) and `cli && npm test` are both required to pass; CI runs both plus `check-manifest`, `check-docs`, and `check-index` before packaging a release.

`cli/` has its own independent `package.json`/`node_modules` — a root-level dependency upgrade doesn't touch it, and vice versa. This is deliberate, not an oversight: `cli/` is a standalone, independently-published npm package, and consolidating `node_modules` via npm/pnpm workspaces would risk a phantom dependency — `cli/` code accidentally resolving something only because it's hoisted from the toolkit's own (much larger, react/vite-heavy) dependency tree, working locally, then breaking for every real `npm install -g toolcrib` user, whose install has no access to this repo's other project at all. There's no automated check guarding against that for `cli/` the way `build-release.js` validates it for the toolkit's own vendored source, so the isolation is standing in for that missing safety net. Considered and rejected for this reason — don't "helpfully" merge them without adding that check first.

### Mandatory: a co-located test for any component whose spread ordering matters

**Any component that both spreads `{...props}` (or `cloneElement`s a child) and computes a value from other props/state/context that must win over what a consumer might pass under the same name gets a co-located test asserting that exact scenario — not just correct ordering in the source, a test proving it.** This is the enforcement half of the general spread-ordering rule documented under "Theme overrides" below; that section explains *why* the ordering matters and how the `SubmitButton` bug happened, this section makes writing the ordering correctly not the only bar — a future refactor that accidentally reorders it needs something to fail. `SubmitButton`'s own `Form.test.tsx` regression test (`'stays disabled while submitting even when the consumer passes their own disabled prop'`) is the template: render with the consumer explicitly passing the colliding prop, put the component into the state that must win, assert the computed value survived.

**One-time audit performed 2026-09-04, per `.plans/toolcrib-defect-pindown-plan.md`'s P1 item 6 — clean result, nothing to fix.** Every `{...props}`-spreading component in `src/components/**` (17 files) was checked for the specific shape that caused this bug twice before (`SubmitButton`, and originally `Splitter.Panel`/`UIGroup`/`Popup`'s `cloneElement` trigger cloning): a value computed from state/props that must win, positioned relative to the spread. Result: every one of them already applies its computed values (typically a `style` object, sometimes a named prop like `disabled` or `id`) *after* `{...props}`, correctly. `Content.Grow`'s `tabIndex={0}` is the one case placed *before* the spread — deliberately, with its own inline comment explaining that an explicit consumer-supplied `tabIndex` should win there, the opposite of `SubmitButton`'s case; not a bug. `SubmitButton` remains the only component in the codebase using the whole-object `(props) => {...}` shape (confirmed via a repo-wide search for `React.FC<...Props> = (props) =>`) — that shape is exactly what let `props.disabled` survive inside the spread in the first place, since every other component destructures the colliding names out into their own variables before spreading `...props`, which removes the collision by construction regardless of ordering. All three `cloneElement` call sites (`Splitter.tsx`, `Overlay/Drawer.tsx`, `UIGroup.tsx`) are the already-fixed, CSS-first/context-based versions this file's "Theme overrides" section documents — no new instance of the original bug shape exists today. Re-run this same audit (grep `\.\.\.(rest)?[Pp]rops` under `src/components`, then check each match's ordering) if a new component introduces either shape.

### `act()` warnings are not noise — they mean the assertion may be racing the update

**A passing test with an `act()` warning in its output is not proof the behavior is correct.** The warning means a React state update happened outside the envelope React Testing Library wraps in `act()` for you, which means the assertion that follows isn't guaranteed to run against the DOM *after* that update actually committed — it may be reading a stale snapshot that happens to satisfy the assertion anyway, this run, on this machine. Treat every `act()` warning in test output as a real bug in the test (not the component) until proven otherwise — never as acceptable console noise to scroll past. Found for real, five separate times across five different files in the same CI log at once — different surface, same root cause every time: something triggered a state update through a path RTL doesn't already wrap.

**Diagnose which path first, then apply the matching fix:**
1. **The test itself directly triggers the update, through something other than `fireEvent`/`render`** — a raw `requestAnimationFrame`/`setTimeout` callback the component scheduled, a callback prop invoked directly instead of via a simulated DOM event, or `vi.advanceTimersByTime(...)` when the timer's own callback causes a `setState`. Fix: wrap that exact call in `act()` — synchronous: `act(() => { ... })`; anything that also needs a microtask/frame to resolve: `await act(async () => { ... })`. Examples: `DataTable.test.tsx`'s scroll-throttling `requestAnimationFrame` wait needed the frame itself inside `act()`, not just awaited after; `FileUpload.test.tsx`'s directly-invoked `onProgress` callback needed the same; `Carousel.test.tsx`'s `vi.advanceTimersByTime()` needed it because the autoplay interval's callback synchronously drives several real `setState` calls through the mocked embla instance.
2. **A third-party library schedules its own follow-up effect internally**, landing after the test's own synchronous render/assertion block already returned — `react-aria-components`' `DateSegment`/`Group` internals do this on mount. Nothing in the test *causes* this update, so there's no single call to wrap — add a trailing `await act(async () => {})` at the end of the test (making it `async` if it isn't already) to flush it before the test function returns. See `TimeField.test.tsx`.
3. **The component under test genuinely needs `useLayoutEffect`** (with its own documented reason — see `Splitter.tsx`'s comment on why `useEffect` wasn't sufficient there) **and the test renders it via `renderToString`.** This is React accurately describing an unavoidable SSR/CSR asymmetry (`useLayoutEffect` cannot run during server rendering, by React's own design), not a test mistake, and not something to "fix" by wrapping in `act()` — `renderToString` isn't async and has nothing to flush. Scope a `vi.spyOn(console, 'error').mockImplementation(() => {})` around just the `renderToString` call(s) that need it, restore it (`mockRestore()`) immediately after, and comment why. See `Splitter.test.tsx`'s SSR-determinism regression test.
4. **A raw DOM method call — `.focus()`, `.blur()`, `.click()` — invoked directly instead of through `fireEvent`.** Unlike `render`/`fireEvent`, these are native DOM APIs React Testing Library doesn't auto-wrap in `act()` at all, so any state update they trigger (a library's own focus-tracking hooks, e.g.) happens completely outside `act()`, not merely deferred. The tell that distinguishes this from case 1/2: escalating `await act(async () => { await new Promise(r => setTimeout(r, <bigger number>)) })` flush delays do **nothing** — because the update already happened, synchronously, before the flush ever ran. Fix: wrap the raw call itself in `act()` (`act(() => { el.focus(); fireEvent.keyDown(el, ...); })`), not by flushing after it. Found for real in `TimeField.test.tsx`'s keyboard-edit test: four separate "not wrapped in act" warnings, all traced to one un-wrapped `hour.focus()` line, and real time was lost first assuming it was a timing problem before finding the actual cause.

**Never wrap a whole test — let alone a whole file — in a blanket `console.error`/`console.warn` mock as a shortcut to make an `act()` warning stop appearing in output.** That doesn't fix the underlying race (case 1/2) or silences a legitimate, understood warning too broadly (case 3) — either way it also swallows the *next* real regression's error output in the same test, which is strictly worse than the noise it was hiding. Scope any suppression to the exact call(s) producing the one expected, understood warning, restore immediately after, and leave every other assertion in the file able to fail loudly on a real `console.error`.

### jsdom's environment gaps fail silently, not loudly — diagnose "won't open" as a missing API first

A missing browser API in jsdom doesn't throw where you'd expect — it fails exactly where the component calls it, silently, and the actual symptom shows up somewhere else entirely: a coverage report with a suspiciously-untested branch, or a test that "settles" for asserting a displayed default instead of ever changing a value. Found for real raising this suite's coverage 86%→95% (commit `88032bb`): every `<Select>`-based interaction had been untestable for the project's entire prior history, because jsdom has no `scrollIntoView` and Radix's `<Select>` `Content` calls it on mount — no test anywhere had ever actually opened one and picked an option. Polyfilled once, centrally, in `setup.ts` (see its own comment) rather than per-file — the same treatment `ResizeObserver` already got there for `Switch`/other Radix primitives that call `react-use-size` internally. When a Radix-based interaction test won't do the thing it's testing at all, check for a missing jsdom API before assuming the component (or the test) is wrong.

Two related gotchas from the same session, worth knowing before writing a Radix interaction test:
- **`<DropdownMenu>` (and similar Radix menu primitives) open on `pointerdown`, not `click`** — `fireEvent.click` on the trigger is a silent no-op (no error, the menu just never opens). Use `fireEvent.pointerDown`.
- **A `<Select>` trigger's `textContent` right after selecting an option includes the item's own `✓` `ItemIndicator`, not just its label** — comparing with `toBe` breaks; use `toContain`, or read the label before the click.

### React Aria Components tests need different assumptions than this codebase's Radix ones

`DatePicker`/`Calendar`/`TimeField` are built on `react-aria-components`, not Radix — its DOM/ARIA conventions genuinely differ from every other overlay/form primitive here, confirmed the hard way while building them:
- State is reflected via `data-selected`/`aria-disabled`, not this codebase's own Radix `data-state` convention used everywhere else.
- A calendar cell's accessible name is the **full formatted date** ("Sunday, March 15, 2026"), not the bare day number — `getByRole('button', { name: /15/ })` is a real footgun: it works by accident (substring match) until a coincidental collision breaks it. Query by the full label, or scope to a container first (see `DatePicker.test.tsx`'s `getDayCell` helper).
- `useCalendar` (and by extension `<Calendar>`) **appends the currently-visible month/year to whatever `aria-label` you give it** — an exact-match assertion against just the label you passed fails; use a prefix match instead.
- Collection-based `react-aria-components` (`ListBox`, `Menu`, `GridList`, and `Breadcrumbs`) only accept **direct** children — violating this fails silently, with no dev-mode warning, unlike most of this codebase's other composition patterns. Likely applies to any other collection-based primitive from the same library; check directly rather than assuming plain-DOM composition rules apply the next time one gets wrapped.

Dump the actual rendered markup when a `react-aria-components`-based test's first assertion attempt is wrong, rather than guessing at a second or third selector — every gotcha above was only found that way.

### axe-core can false-positive on `color-mix()`/relative-color CSS — verify the real contrast math before trusting a red X

Turning the one-time WCAG pass into a standing `axe-core` + Playwright gate (commit `a63d948`) surfaced a real tooling limitation, not a real defect: Chromium serializes a computed `color-mix()`/`hsl(from ...)` value as `oklab(...)`/`color(srgb ...)`, and axe-core 4.13.0 can't parse that — it reports a contrast violation regardless of the actual ratio. Confirmed by hand-computing the real WCAG luminance/contrast for the flagged elements (5–6:1, comfortably over the 4.5:1 floor) before concluding axe was wrong, not the CSS. The fix was switching the flagged rule to a plain `hsvToCSS()`-generated literal (a real palette-engine value, not a live CSS color function), not disabling the check wholesale — `color-contrast` is disabled in the axe spec only where this exact false-positive shape was confirmed, with a comment explaining why.

A second false lead from the same session, worth naming so it doesn't cost someone else the same time: a flaky-looking pass/fail difference between running one test in isolation vs. the full file looked like a parallelism/timing race at first. It wasn't — a prior test's tab-switch click left the real mouse cursor hovering an element, and a `:hover` rule using `color-mix()` was the actual trigger. Move the mouse away before an axe scan if a contrast result seems to depend on what ran before it in the same file.

## TypeScript

Full TypeScript coverage on everything — this is what keeps an AI consuming the toolkit from hallucinating props or types that don't exist. Run `npx tsc` (root) before considering a change done; it's `noEmit`, just a type-check.

**Root `typescript` is on the `7.x` line; `scripts/` is pinned separately to `6.0.3`, in its own `scripts/package.json`.** These used to be one pin, held back at `6.x` repo-wide, because TypeScript 7's package export is reduced to `{ version, versionMajorMinor }` — `createSourceFile`, `ScriptTarget`, `isVariableStatement`, and the rest of the classic Compiler API that `scripts/lib/extract.js` depends on for manifest/docs generation are simply absent in 7.x, not renamed or deprecated. A whole-repo trial confirmed `extract.js` was the *only* thing that broke; nothing else in `src/`, `demo/`, or `tsc`'s own type-checking needed anything the classic API provided. Splitting `scripts/` into its own `package.json` (with `typescript: 6.0.3` as its sole dependency) let root move to `7.x` for its own build/type-check without waiting on `extract.js`'s narrower requirement — Node resolves `import ts from 'typescript'` starting from the importing file's own directory, so `scripts/generate-manifest.js` always gets `6.0.3` from `scripts/node_modules` regardless of what root has installed, with no workspace tooling or explicit path juggling required. `scripts/` needs its own `npm install` run once, separately from root's — a fresh clone or CI job that only runs root's `npm ci` won't have `scripts/node_modules` populated. If `extract.js` (or anything else under `scripts/`) ever needs a second dependency, add it to `scripts/package.json`, not root's.

Don't bump `scripts/package.json`'s `typescript` past `6.x` without first confirming `extract.js`'s classic-API surface still exists in whatever version you're moving to — the same caution that used to apply repo-wide now applies only there.

## Linting

`npm run lint` (root) runs ESLint against `src/`/`demo/`, scoped deliberately to just `eslint-plugin-react-hooks`'s rules (rules-of-hooks, exhaustive-deps, and its newer v7 "Rules of React" set — set-state-in-effect, refs, purity, etc.) — the actual React-correctness anti-patterns this exists to catch, not `typescript-eslint`'s or `eslint-plugin-react`'s own "recommended" presets. A first real run with those broader presets enabled produced 229 findings, almost entirely `@typescript-eslint/no-explicit-any` (a style opinion, already largely redundant with this file's own `noUnusedLocals`/`noUnusedParameters`) and `react/no-unescaped-entities` (a low-value rule flagging ordinary apostrophes in prose-heavy JSX). Adding either back is a legitimate future option, but as its own deliberately-triaged decision, not something a "recommended" preset's broader scope should bundle in by default.

**`eslint`/`typescript-eslint` live in `scripts/package.json`, not root's, for the identical TS-7 reason above** — `typescript-eslint` hard-fails at import time against TS 7 (confirmed directly: `"typescript-eslint does not support TS 7.0"`, the same class of Compiler-API-removal break as `extract.js`'s), so it joined `scripts/`'s existing isolated `typescript@6.x` rather than needing a third isolated package.json of its own. Root's `"lint"` script invokes `scripts/`'s eslint binary directly (`node scripts/node_modules/eslint/bin/eslint.js --config scripts/eslint.config.js src demo`), not via `npm --prefix scripts` — two non-obvious things had to be verified directly (not assumed) to get this working at all, both documented at length in `scripts/eslint.config.js`'s own header comment:

1. **ESLint flat config resolves its "base path"** (the directory a target file must be *relative to*, for `files`/`ignores` matching) **from `cwd`, not from the config file's own location**, whenever `--config <path>` is passed explicitly (confirmed in eslint's own `config-loader.js`: `basePath = cwd` unconditionally on that branch). Invoking with cwd = `scripts/` made every file under root's `src/`/`demo/` resolve as "outside the base path" and get silently ignored — cwd has to stay at root, while the config *file* itself still lives in `scripts/` purely so its own `import 'typescript-eslint'` resolves from that directory's isolated `node_modules` (ES module bare-specifier resolution is based on the importing file's disk location, not cwd — the two concerns are independent).
2. **A leading `../` in a `files`/`ignores` glob pattern is unreliable**, and so is an absolute path built via `path.join`/`path.resolve` **on Windows specifically** — `@eslint/config-array` matches a target file by converting its absolute path to one *relative to basePath* first (`path.relative(basePath, fullPath)`), so an absolute pattern can never match regardless of platform; separately, `path.join`/`path.resolve` produce backslash-separated paths on Windows, which glob engines treat as escape characters rather than path separators, silently neutering `**`/`*` wildcards even when the base-path issue is otherwise fixed. Both were found by real trial and error against actual `npm run lint` output ("all files ignored," then "no matching configuration"), not reasoned out in advance — if `scripts/eslint.config.js` ever needs new `files`/`ignores` entries, keep them as plain relative-to-root strings (`'src/**/*.{ts,tsx}'`), not absolute paths or anything passed through `path.join`.

If a genuine anti-pattern finding can't be fixed cleanly without real behavioral risk (a legitimate "subscribe to an external system" effect that also needs an eager initial read, e.g.), a targeted `eslint-disable-next-line` with a comment justifying *why* is correct — but the comment must be the line immediately before the flagged code, not the first line of a multi-line explanation block, or ESLint disables the wrong line entirely (confirmed the hard way: a 3-line comment followed by `// eslint-disable-next-line` on its own line, then the code, disables nothing on the actual target line and reports the directive itself as unused).

## Cutting a release

Only when the maintainer explicitly asks for a version bump — not something to do proactively alongside an unrelated change. `.github/workflows/release.yml` triggers on a pushed `v*` tag and does the actual build/package/publish; everything below is what has to be true *before* that tag gets pushed, since the workflow verifies the tag matches `package.json` and will fail the whole release if the two disagree.

1. **Bump the root `package.json` `"version"` field only** — never `cli/package.json`'s or `mcp/package.json`'s. Both the CLI (`toolcrib` on npm) and the local MCP server (`toolcrib-mcp` on npm, see `mcp/CONTRIBUTING.md`) are independently-versioned, independently-published packages; neither's version has any relationship to the toolkit's, or to each other's. A toolkit release doesn't touch either of their versions. `mcp/` ships zero vendored `ai-docs/` content of its own, so its release cadence is decoupled from toolcrib's content releases entirely — a new `toolcrib-mcp` version is only needed when its own server logic changes, never because toolcrib shipped a new component.
2. **Regenerate, don't hand-edit, everything version-derived**: `npm run generate-manifest && npm run generate-docs && npm run generate-index`. `component-manifest.json` embeds `package.json`'s version directly — this is what keeps it in sync, the same "generated, not hand-maintained" discipline as everything else these three commands own.
3. **Verify for real before tagging, not just trust the diff looks right**: `npm test` (root), `npx tsc --noEmit`, `cd cli && npm test`, then `npm run check-manifest`/`check-docs`/`check-index` (should all report clean since step 2 already regenerated them — a real failure here means something in step 2 didn't actually converge). This is the same set `release.yml` itself runs — running it locally first means a bad release fails on your own machine, not as a public, half-published GitHub Actions run.
4. **Re-check current source against `.plans/toolcrib-defect-pindown-plan.md`'s taxonomy and this file's own anti-pattern entries, once, before tagging** — added 2026-09-04, after that plan's own diagnosis: a documented anti-pattern only helps once someone is already looking for it by name at the moment new code could repeat it, and nothing about a prose write-up forces that lookup to happen on its own. `npm test`/`tsc`/the manifest-drift checks in step 3 all verify internal self-consistency (code matches its own types, generated docs match their source); none of them verify *external* consistency (real-browser behavior, cross-file wiring, cross-platform paths) — which is exactly the shape every recurring defect class in that plan has taken. This is a full-repo read, not a per-file check: skim the plan's six taxonomy classes and this file's own anti-pattern write-ups, then spot-check recent changes against each rather than assuming a class that bit the project once can't bite it again in a new file. Same "found once vs. found forever" gap the `{...props}`-ordering rule below and the `.ai-focus-ring` fix both already illustrate — this step exists because relying on that lookup happening spontaneously has already failed to prevent a second occurrence more than once.
5. **Re-verify against the real consumer apps: `feed-farmer-pwa` and `founders-desk`** — added 2026-09-04. These are toolcrib's de facto integration suite, not just example content — the `Form.tsx` `onSubmit`-receives-raw-values bug that prompted the defect-pindown plan in the first place was found by building `founders-desk`, not by anything in this repo's own unit suite, because it's the one mechanism that actually exercises cross-file wiring (a schema's parsed output reaching a real consumer's real `.toFixed()` call) end-to-end. Before tagging: re-apply current `main` into each app (`toolcrib merge` against their vendored copy, or a fresh `toolcrib init` diffed against their current state) and run each app's own `tsc`/test suite. A real failure here is a real regression this repo's own tests structurally can't see — fix it before the tag, not after a consumer reports it.
6. **Commit and push to `main` first, tag second** — the tag has to point at a commit where `package.json`'s version already matches what's about to be tagged, or `release.yml`'s own "Verify tag matches package.json version" step fails the whole workflow.
7. **Tag and push**: `git tag -a vX.Y.Z -m "vX.Y.Z" && git push origin vX.Y.Z`. This is what actually triggers the release — a public, visible action (a new GitHub Release, downloadable by anyone) — so this step specifically needs the maintainer's go-ahead, not just steps 1-5.
8. **Watch it through, don't assume it succeeded**: `gh run watch <run-id> --exit-status` (find the run via `gh run list --workflow=release.yml --limit 1`) blocks until the workflow finishes and surfaces a real failure instead of a silently abandoned release. Confirm the release actually exists after: `gh release view vX.Y.Z`.

This whole sequence is a maintainer-initiated action end to end — steps 1-5 are safe/reversible (local commits, nothing public yet), but step 7 is not (a pushed tag triggers a real public release immediately, no draft/review stage in between) and should never happen without the maintainer having explicitly asked for that specific version number first.
