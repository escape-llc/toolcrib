# Cutting a toolcrib release

Split out of `AGENTS.md` (see that file's own "Cutting a release" section) since this whole sequence is invoked at exactly one specific, rare, maintainer-initiated moment — read this file in full only when the maintainer explicitly asks for a version bump, not as part of every session's standing context.

Only when the maintainer explicitly asks for a version bump — not something to do proactively alongside an unrelated change. `.github/workflows/release.yml` triggers on a pushed `v*` tag and does the actual build/package/publish; everything below is what has to be true *before* that tag gets pushed, since the workflow verifies the tag matches `package.json` and will fail the whole release if the two disagree.

1. **Bump the root `package.json` `"version"` field only** — never `cli/package.json`'s or `mcp/package.json`'s. Both the CLI (`toolcrib` on npm) and the local MCP server (`toolcrib-mcp` on npm, see `mcp/CONTRIBUTING.md`) are independently-versioned, independently-published packages; neither's version has any relationship to the toolkit's, or to each other's. A toolkit release doesn't touch either of their versions. `mcp/` ships zero vendored `ai-docs/` content of its own, so its release cadence is decoupled from toolcrib's content releases entirely — a new `toolcrib-mcp` version is only needed when its own server logic changes, never because toolcrib shipped a new component.
2. **Regenerate, don't hand-edit, everything version-derived**: `npm run generate-manifest && npm run generate-docs && npm run generate-index`. `component-manifest.json` embeds `package.json`'s version directly — this is what keeps it in sync, the same "generated, not hand-maintained" discipline as everything else these three commands own.
3. **Verify for real before tagging, not just trust the diff looks right**: `npm test` (root), `npx tsc --noEmit`, `cd cli && npm test`, then `npm run check-manifest`/`check-docs`/`check-index` (should all report clean since step 2 already regenerated them — a real failure here means something in step 2 didn't actually converge). This is the same set `release.yml` itself runs — running it locally first means a bad release fails on your own machine, not as a public, half-published GitHub Actions run. Also run `GITHUB_TOKEN=$(gh auth token) npm run generate-security-advisories` (see `security-advisories.json`'s own section in `AGENTS.md`) — unlike the other three, this one isn't "version-derived" so it doesn't belong in step 2, but a release is exactly the right checkpoint to pick up any CodeQL alert fixed and merged since the last check; commit the diff if it produced one.
4. **Re-check current source against `.plans/toolcrib-defect-pindown-plan.md`'s taxonomy and `AGENTS.md`'s own anti-pattern entries, once, before tagging** — added 2026-09-04, after that plan's own diagnosis: a documented anti-pattern only helps once someone is already looking for it by name at the moment new code could repeat it, and nothing about a prose write-up forces that lookup to happen on its own. `npm test`/`tsc`/the manifest-drift checks in step 3 all verify internal self-consistency (code matches its own types, generated docs match their source); none of them verify *external* consistency (real-browser behavior, cross-file wiring, cross-platform paths) — which is exactly the shape every recurring defect class in that plan has taken. This is a full-repo read, not a per-file check: skim the plan's six taxonomy classes and `AGENTS.md`'s own anti-pattern write-ups, then spot-check recent changes against each rather than assuming a class that bit the project once can't bite it again in a new file. Same "found once vs. found forever" gap `AGENTS.md`'s `{...props}`-ordering rule and `.ai-focus-ring` fix both already illustrate — this step exists because relying on that lookup happening spontaneously has already failed to prevent a second occurrence more than once.
5. **Run the three security/accessibility/CI-workflow audit skills before tagging: `owasp-review`, `aria-compliance-review`, `actions-injection-review`** — added following a review pass of toolcrib's own docs/tooling, closing a real discoverability gap: these live under `.claude/skills/` and audit toolcrib's own repo specifically (its CLI's release/patch pipeline, its `e2e/accessibility.spec.ts` coverage gaps, its own `.github/workflows/*.yml`), but nothing in the release checklist previously named them as something to actually *run*, not just something that happens to exist. In Claude Code, invoke each directly (`/owasp-review`, `/aria-compliance-review`, `/actions-injection-review`); on a tool that can't load a Claude Code skill, read `.claude/skills/<name>/SKILL.md` directly instead — same checklist content either way, just without the slash-command convenience, since it's a plain markdown file with no access barrier beyond not knowing to look. Fix or file an issue for anything a pass finds before the tag goes out, same discipline as step 4's own anti-pattern-recheck rule.
6. **Re-verify against the real consumer apps: `feed-farmer-pwa` and `founders-desk`** — added 2026-09-04. These are toolcrib's de facto integration suite, not just example content — the `Form.tsx` `onSubmit`-receives-raw-values bug that prompted the defect-pindown plan in the first place was found by building `founders-desk`, not by anything in this repo's own unit suite, because it's the one mechanism that actually exercises cross-file wiring (a schema's parsed output reaching a real consumer's real `.toFixed()` call) end-to-end. Before tagging: re-apply current `main` into each app (`toolcrib merge` against their vendored copy, or a fresh `toolcrib init` diffed against their current state) and run each app's own `tsc`/test suite. A real failure here is a real regression this repo's own tests structurally can't see — fix it before the tag, not after a consumer reports it.
7. **Commit, PR, merge to `main` — then tag, not before.** `main` is a protected branch; a direct `git push origin main` is rejected outright (confirmed live, not assumed), so this step is the standard issue/branch/PR/CI-green/squash-merge sequence in `WORKFLOW.md`, same as any other real change — not a special case just because it's a release commit. Once merged, `git checkout main && git pull --ff-only` before tagging, so the tag points at a commit where `package.json`'s version already matches what's about to be tagged (required — `release.yml`'s own "Verify tag matches package.json version" step fails the whole workflow otherwise) *and* that commit's own PR has already gone through this repo's full CI, not just a local `npm test` run.
8. **Tag and push**: `git tag -a vX.Y.Z -m "vX.Y.Z" && git push origin vX.Y.Z`. This is what actually triggers the release — a public, visible action (a new GitHub Release, downloadable by anyone) — so this step specifically needs the maintainer's go-ahead, not just steps 1-6. The same `v*` tag push also triggers `screen-reader.yml` (moved off every-push/PR and onto this exact trigger — see that file's own header comment) — real NVDA/screen-reader verification wasn't worth its ~4-6 minute cost on every single push once confirmed it was never a required status check to begin with, but a release is exactly the checkpoint that cost is worth paying at.
9. **Watch it through, don't assume it succeeded**: `gh run watch <run-id> --exit-status` (find the run via `gh run list --workflow=release.yml --limit 1`) blocks until the workflow finishes and surfaces a real failure instead of a silently abandoned release. Confirm the release actually exists after: `gh release view vX.Y.Z`. **Also check `screen-reader.yml`'s own run for this same tag** (`gh run list --workflow=screen-reader.yml --limit 1`) before considering the release done — it runs independently, isn't wired as a `needs:` gate on the release job itself (deliberately: NVDA/speech-capture is self-documented as less deterministic than this repo's other checks, and hard-blocking an irreversible public release on a flakier signal risks blocking a legitimate one for the wrong reason — same non-gating-but-mandatory-to-read tradeoff `AGENTS.md`'s own Gemini-review section already applies), so nothing else will surface a real screen-reader regression here except a human actually looking.
10. **Post a release-summary discussion under "Announcements", once the release is confirmed.** Distinct from `SESSION_SUMMARIES.md`'s own "AI Session Summaries" posts (a per-checkpoint friction/process log) and from the Gemini-authored "Show and tell" casual posts (`project_marketing_workflow` memory) — this is a real, maintainer-authored release note summarizing `git log v<prev>..v<new> --oneline` since the last tag, **synthesized into real prose ordered by actual impact (biggest first), not a mechanical list of every commit/PR title**. Skim the log, group related commits into their real underlying story (a feature area maturing across several PRs, a bug found-and-fixed during release prep, a process change), and write it the way a maintainer would describe the release to someone who wasn't watching it happen commit by commit — see discussion #504 (v0.15.0) for the calibration this is aiming for. Post via `gh api graphql` with a `createDiscussion` mutation, body content passed through a file (`-F body=@path`, never inline in `-f`, per the `gh_graphql_body_to_file` habit — this content is always too long/markdown-heavy for reliable inline shell-quoting). Cached GraphQL node IDs (confirmed 2026-09-17, same caveat as `SESSION_SUMMARIES.md`'s own cached IDs — re-fetch via `repository.discussionCategories` if a mutation fails against them): repository (`escape-llc/toolcrib`) `R_kgDOTwhGaA`; "Announcements" category `DIC_kwDOTwhGaM4DDQXw`.

This whole sequence is a maintainer-initiated action end to end — steps 1-6 are safe/reversible (local commits, nothing public yet), but step 8 is not (a pushed tag triggers a real public release immediately, no draft/review stage in between) and should never happen without the maintainer having explicitly asked for that specific version number first. Step 10 is also a real public action (a visible Discussions post under the maintainer's own account) but, unlike step 8, doesn't need a separate go-ahead each time — posting it is now the standing default for every tag, the same "do it, don't ask first" treatment `feedback_push_and_post_standing` already established for regular work checkpoints.
